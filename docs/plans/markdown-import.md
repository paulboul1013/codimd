# 從歷史介面匯入 Markdown

狀態：已依本計畫完成實作與專項、瀏覽器、資料庫驗收。預設完整測試仍有基準版本也重現的 realtime 逾時。詳見 [pstack 重點流程報告](../reports/markdown-import-pstack-summary.md) 與 [完整紀錄](../reports/markdown-import-pstack-detail.md)。

## 目標

從歷史介面選取本機 UTF-8 的 `.md`、`.markdown` 或 `.txt` 檔案，以檔案內容建立新筆記。副檔名不區分大小寫。優先重用既有建立筆記的流程，以最少改動提供完整的匯入體驗。

已確定在歷史介面新增有文字標示的「匯入 Markdown」獨立按鈕，每次只接受一個檔案。既有歷史 JSON 匯入維持原有入口。

術語見 [CONTEXT.md](../../CONTEXT.md)。

## 已確認的實作

| 項目 | 建立空白筆記 | 帶正文建立筆記 |
| --- | --- | --- |
| 路由 | `GET /new` | `POST /new` |
| 入口 | `lib/response.js` 的 `newNote` | 同一個 `newNote` |
| 請求內容 | 無正文 | 原始 Markdown 字串，使用 `text/markdown` 或 `text/plain` |
| 預設內容 | 空正文會觸發模型載入預設範本 | 非空正文直接作為筆記內容 |
| 擁有者 | 已登入者為擁有者，訪客受 `allowAnonymous` 限制 | 相同 |
| 初始權限 | 有擁有者使用 `defaultPermission`，訪客使用 `freely` | 相同 |
| 版本 | 模型建立後儲存初始版本 | 相同 |
| 歷史 | `newNote` 為已登入者更新歷史 | 相同 |
| 成功回應 | 重新導向新筆記網址 | 相同 |

來源：

- `lib/routes.js:65`：兩條 `/new` 路由。
- `lib/utils.js:30`：Markdown 文字 parser，限制為 10 MiB。
- `lib/response.js:92`：正文長度檢查、移除 CR 字元、權限、建立、歷史與重新導向。
- `lib/models/note.js:91`：預設範本、初始權限與初始版本。
- `public/js/cover.js:325`：現有選檔與歷史 JSON 合併流程。
- `public/js/index.js:1359`、`public/js/index.js:1513`：編輯器中的既有匯入會修改已開啟筆記，需要編輯器狀態。

既有正文長度限制為 `config.documentMaxLength`，預設 100000 個 JavaScript 字串長度單位。此限制與 parser 的位元組限制不同，沿用時都會生效。

標題與標籤有一項需要注意的差異：歷史更新會由正文解析標題與標籤，但 `newNote` 沒有為非空正文設定資料庫的 `title`。`lib/models/note.js:336` 已有 `parseNoteTitle`，規則為 front matter 的 `title`、第一個可用的 H1、最後使用 `Untitled`。計畫在帶正文建立時重用此函式，立即設定資料庫標題。空正文的建立仍由模型處理預設範本與範本標題。

## 修改步驟

1. 修改 `public/views/index/body.ejs`。
   - 在歷史工具列新增有文字標示的「匯入 Markdown」按鈕與單檔選擇器，不啟用 `multiple`。
   - 使用 `accept` 提示 `.md`、`.markdown` 與 `.txt`。前端再檢查副檔名，避免依賴作業系統提供的 MIME 類型。
   - 登入者及設定允許建立筆記的訪客可看見按鈕，沿用新增筆記的使用資格。按鈕可在窄螢幕操作。
   - 提供可見的錯誤訊息位置，避免選檔失敗時沒有回饋。
2. 修改 `public/js/cover.js`。
   - 為新選擇器註冊獨立處理函式，借鑑現有 `FileReader`，以 UTF-8 讀取單一檔案。
   - 取消選檔時直接返回。檔名轉為小寫後檢查副檔名。
   - 若讀取結果移除 CR 字元後為空，顯示「檔案沒有內容」，不送出建立請求。不使用 `trim()` 改寫空白內容的語意。
   - 以 `text/markdown; charset=UTF-8` 與目前登入憑證，將原始正文送至 `${serverurl}/new`。
   - 使用專案已有採用的原生 `fetch`，跟隨重新導向並讀取最終 URL。僅在回應成功且 URL 為目前站點與部署路徑下的新筆記網址時，於目前分頁導頁。
   - 登入重新導向、413、500、讀檔失敗與網路錯誤均顯示可理解的訊息，不自動重送建立請求。
   - 處理期間停用選檔，失敗後恢復並清空選擇器，使同一檔案可以再次選取。
3. 小幅修改 `lib/response.js` 的 `newNote`。
   - 非空正文使用既有 `models.Note.parseNoteTitle(body)` 設定建立時的 `title`。
   - 保留既有正文長度檢查、CR 正規化、擁有者、權限、歷史與重新導向。
   - 空正文不指定解析後的標題，維持模型載入預設範本的行為。
   - 此修正會讓其他以非空正文呼叫 `POST /new` 的使用者也立即取得正確資料庫標題。
4. 在 `locales/` 補齊新增按鈕與錯誤訊息的翻譯鍵，提供繁體中文文案，其他語言依既有英文回退慣例處理。
5. 加入必要回歸測試，執行下列驗收案例並保留 UI 截圖。

沿用 `newNote` 與模型 hooks 處理建立、權限、初始修訂與歷史，不另寫一套建立流程。既有歷史 JSON 的匯入處理維持獨立。

直接帶正文建立只需一次建立操作。先建立空白筆記再寫入正文，會額外載入預設範本、增加更新步驟，且更新失敗時會留下預設筆記，因此採用 `POST /new`。

## 決策樹

- Q1 匯入入口：已選擇新增獨立「匯入 Markdown」按鈕。
- Q2 單次匯入數量：已選擇單一檔案。
- Q3 匯入完成後的頁面位置：已選擇在目前分頁開啟新筆記。
- Q4 空檔處理：已選擇拒絕空檔，顯示「檔案沒有內容」。判定考慮既有移除 CR 的正規化，保留只有空白或 LF 的內容。
- Q5 標題規則：已選擇沿用正文規則，沒有標題時為 `Untitled`，檔名不參與命名。建立時立即寫入標題。
- Q6 檔案範圍：已選擇 UTF-8 的 `.md`、`.markdown` 與 `.txt`，副檔名不區分大小寫。`.txt` 內容亦作為 Markdown 正文匯入。

## 驗收案例

| 情境 | 預期結果 |
| --- | --- |
| 中文 UTF-8 正文，包含 front matter、H1、標籤與 CRLF | 建立一份新筆記並在目前分頁開啟；正文只經既有正規化，標題依原有優先順序解析，歷史標籤正確 |
| `.MD`、`.Markdown`、`.TXT` | 均可匯入，檔名不會變成文章標題 |
| 正文只有 H1，或沒有可用標題 | 分別採用 H1 或 `Untitled`，建立當下的資料庫標題即正確 |
| 0 bytes 或只有 CR 的檔案 | 顯示「檔案沒有內容」，不送建立請求、不留下範本筆記 |
| 只有空格或 LF 的非空檔案 | 沿用正文語意，不以 `trim()` 拒絕或改寫內容 |
| 取消選檔、不支援的副檔名、讀檔失敗 | 不建立筆記，必要時顯示錯誤，可重新選檔 |
| 超過正文長度或 parser 限制 | 顯示錯誤，不將錯誤頁視為匯入成功 |
| 已登入者或允許匿名建立的訪客 | 擁有者、初始權限與歷史行為與原有新增筆記流程一致 |
| 登入失效且禁止匿名建立 | 辨識首頁登入重新導向，不誤判成功，不建立筆記 |
| 500 或網路錯誤 | 顯示失敗，可再次選檔，不自動重送；網路中斷時不保證伺服器尚未建立筆記 |
| 回到歷史介面再次選同一個檔案 | 可再次操作；匯入本身的語意為建立新筆記，不覆寫既有筆記 |
| 讀取初始修訂 | 第一份修訂已含匯入正文，不含中間範本內容 |
| 原有 GET /new 與空正文建立 | 仍使用部署設定的預設範本及其標題 |
| 原有無副檔名歷史 JSON 匯出與匯入 | 仍可正常合併歷史清單 |
| 子路徑部署與窄螢幕 | 請求和導頁路徑正確，匯入按鈕可操作 |

## 文件與驗證範圍

實作時使用 Node.js v16.20.2。

1. 在 `test/response/newNote.test.js` 以既有 Mocha、Sinon 與 mock-require 測試非空正文的初始標題、空正文保留範本語意、權限限制與超長內容。測試後還原 mock。
2. 執行 `npm test` 與 `npm run build`，確認 lint、JSON、既有測試與前端編譯。
3. 實際啟動程式，以瀏覽器驗證上表的核心流程，檢查新筆記的正文、標題、歷史與初始修訂。針對空檔確認沒有建立請求。
4. 保留歷史頁按鈕、空檔提示與成功匯入文章的截圖。

驗證結果與原始輸出已收錄於流程報告。專項回歸 39 項通過，瀏覽器驗收 53 項通過，停用計時限制的完整 coverage 為 186 項通過；預設 npm test 的 realtime 逾時仍列為驗證限制。

本方案目前不需要新增套件、資料庫欄位或 API。這是可逆的介面整合，暫無需要另立 ADR 的重大決策。

前端既有程式已有使用原生 `fetch`，但首頁沒有顯式的 fetch polyfill。本計畫沿用專案已有採用的原生 fetch，不新增 polyfill；缺少 fetch 的舊瀏覽器不在本次擴充範圍。
